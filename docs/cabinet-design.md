# Starting cabinet design

Working design notes from the initial plugin discussions. Confirmed direction is separate from questions that still need decisions.

## Confirmed direction

- Start with cabinet setup and ingredient, inventory, and recipe creation. Availability queries are not the first feature milestone.
- Preserve bottles as a first-class concept with bottle-specific properties. Do not replace them with a generic product model solely to accommodate other ingredients.
- Design deliberately for homemade syrups, fresh juice, and other non-bottle ingredients; their representation is still open.
- Supply a curated starting hierarchy with fixed levels and names. Arbitrary hierarchy depth and arbitrary level names are outside the intended scope.
- Use three levels: ingredient category, ingredient family, and ingredient type. Family replaces the previous term subcategory. Exact stored property names and any longer names used to avoid vault conflicts remain undecided.
- Build the default hierarchy from concrete ingredient types upward. Add families and categories where a comprehensible grouping provides useful recipe references or navigation. A complete chain is not the recommended default for every ingredient.
- Parent relationships are optional: a type may have no family, and a family may have no category. Fixed relationship roles keep the schema consistent without requiring every level to be populated.
- All ingredient types must remain equally findable, whether or not they have parents. Missing parents are not an incomplete or invalid state.
- The starting cabinet should be thorough enough to include the base spirits, several common liqueurs, the most common juices, and the most common syrups.
- Preserve the ability to reference a particular bottle in a recipe, support other bottles of the same ingredient type, and find that recipe through its ingredient type and broader classifications.
- Prefer useful opinions while allowing flexibility where it is inexpensive and understandable.

## Obsidian features and portability

- Cabinet setup creates a Base for each resource kind: ingredient categories, families, types, bottles, other stock, and recipes. The Cocktail Cabinet note links to every one of these Bases; it must not present a creation-time snapshot as the current collection.
- Prefer core Obsidian notes, properties, links, and Bases for browsing, filtering, sorting, and ordinary editing. Custom UI needs a concrete benefit beyond those features. Setup preflight, validated creation with ingredient selection, and hierarchy-aware recipe matching currently provide that benefit.
- The useful system belongs to the user in their vault. Disabling or losing Cocktail Cabinet must leave readable, editable notes, meaningful links, documented properties, and live views that work with core Bases alone. With Bases disabled, notes and links remain usable. Plugin settings and private runtime state must not be the sole source of collection data or view definitions.
- The Cocktail Cabinet note, where the ribbon button and **Open cabinet** go, is a short portal (decided 2026-11-24, replacing a page that explained each part and overlapped the guide): it sends newcomers to Getting Started, then links the views and names the commands most likely to be needed or forgotten, grouped as Make a drink, Stock, Shopping, and Ingredients, then lists the guide. Explanation lives in the guide, so the two can't drift. The views that aren't files (**What can I make?**, **What should I buy?**, **Review unlinked ingredients**) are linked too, with `obsidian://cocktail-cabinet?open=…` links the plugin handles (built 2026-11-24); the guide links them where it describes them. Only those views open this way, since any page or app can follow an obsidian:// link, and the links carry no vault, so the page stays the same in every vault. With the plugin off they do nothing. Verified on desktop with two vaults open: each link opened its view in the vault it was clicked in, in under a second. Mobile still to check. The worked example section stays while the examples remain. Links must remain useful after setup rather than describe a permanently empty cabinet.
- The Bases in `<root>/Views/` belong to the plugin (decided 2026-11-06, replacing user-owned views). Users who want a different view copy it into `<root>/Custom views/`, which setup creates and the plugin never writes. Setup creates missing files, replaces views that differ, and preserves notes. The Cocktail Cabinet and Shopping list notes are managed notes, kept current unless edited ([ownership](ownership.md), built 2026-11-21).
- **Keeping views current.** The plugin records, in its data, a root-independent fingerprint of the version of each view it last wrote. On startup it rewrites a view only when the current generated version's fingerprint differs from that record, so Obsidian's own saves (column widths, a sort picked in the toolbar) and a deleted view stay until a release or a setting changes that view. **Refresh cabinet notes** (also a button in settings) rewrites every view that differs or is missing. Comparing file content instead failed in practice: Obsidian re-serializes a Base's YAML when it saves it, so an untouched view no longer matched any generated version.
- Future capabilities should reuse native features where they cover the workflow and justify custom UI where they do not. The shopping list is a Base over the stock and purchasing schema, embedded in its own note.

## Collection coherence and ingredient resolution

The plugin should help users keep their cocktail system clean, clear, and working. Recipe creation, note enhancement, imports, and ingredient creation should help reuse existing ingredient identities and maintain useful links. Successful parsing alone does not fulfill this goal.

- Look for existing notes using names, filenames, aliases, and ingredient context before steering users toward creation. Surface likely matches and explain uncertainty; a failed text match does not establish that an ingredient is absent.
- When offering creation, help users review possible duplicates and choose the appropriate resource kind. Different recipe wording, spelling, or a parenthetical brand may refer to an existing identity. A bottle and its ingredient type have distinct roles; a new stock record need not require a new type.
- Preserve recipe specificity and meaningful ingredient distinctions. Matching an identity is separate from finding a substitute; similarity or shared classification alone does not justify merging notes or treating ingredients as identical.
- Keep uncertain ingredients reviewable. Plain text remains a valid choice, with its effect on availability and logging made clear. Users should be able to resolve a link later without recreating the recipe.
- Develop this assistance incrementally across entry points, reusing resolution behavior and the user's existing aliases and relationships. These are product requirements for ongoing development; the current name-based suggestions are an initial implementation, and a complete duplicate-resolution workflow remains future work.

## Ingredient identity and starter content

- The guiding principle for distinguishing ingredients is whether the difference would change the cocktail recipe. This is a practical guideline; recipes vary in specificity, and users need room to customize their own distinctions.
- Default syrup types should distinguish 1:1 simple syrup, 2:1 simple syrup, and probably 2:1 demerara syrup. Do not collapse the defaults to match only the syrups the project owner personally stocks.
- Fruit juice means fresh juice by default. Bottled juice should be possible to track and use without requiring a separate recipe-facing ingredient type solely because it is bottled.
- Preparations such as superjuice or acid-adjusted juice can warrant distinct ingredient types. Their exact representation and default inclusion are still open.
- Included ingredient pages need a basic description and appropriate properties, such as sugar-to-water ratios by weight for sugar syrups. Concentration details may be recorded in the note body; Brix is not a built-in property. Preparation instructions may be included; they are not a commitment to batch tracking or a separate preparation-recipe system.
- The starter catalog should cover common needs with useful content while remaining bounded. The plugin helps people maintain and use their own recipe database; it is not intended to supply a comprehensive recipe database.

## Recipe specificity and hierarchy

- A recipe may reference any supported hierarchy level, including a broad entry such as Rum, as well as a specific bottle. It does not have to select a leaf ingredient type.
- A broad reference permits candidates classified beneath that entry. A narrow reference must not silently broaden to everything sharing a parent: a Rum requirement and an Aged Jamaican Rum requirement have different scopes.
- A broad classification's recipe view includes direct references and recipes referencing its descendant types or their bottles.
- A bottle has at most one ingredient type, representing its recipe role. Broader classification comes through families and categories; substitutions and recipe-specific alternatives should be modeled separately rather than by assigning overlapping types.
- A named bottle remains the recipe's named choice while the existing same-type alternative behavior is preserved. Sharing a broader group alone does not establish a same-type alternative.
- Imports should preserve the specificity supplied by their source. A recipe saying only rum can be created without forcing a narrower selection or inventing one.
- Users may subsequently refine broad requirements to specific ingredient types, as the project owner commonly does for rum recipes. Refinement is optional.

## Approved stock and purchasing design

The [resource schemas](note-properties.md) specify the fields and constraints. Creation forms and resource Bases implement mode-based mL stock, purchasing fields, and shopping flags. Consumption is implemented by **Log this cocktail**, and flagged resources appear in the **Shopping list** note, with a section per kind (decided 2026-11-04, matching the `knowledge` vault's three-table Shopping note). Existing early notes need the documented manual conversion; setup preserves their contents.

- Each bottle or other-stock source explicitly selects `cc-stock-tracking: volume` or `status`. The source's form does not determine its mode; homemade syrup, fresh or purchased juice, and bottles can use either. Creation defaults are volume for bottles and status for other stock.
- Volume tracking stores mL remaining. Bottles use `cc-open-ml` for the open bottle and retain full bottle volume and unopened count; other stock uses `cc-remaining-ml`. Bottle fractions are replaced in new notes. ABV continues to be stored as a fraction. Unknown measured amounts remain distinct from known zero. An empty unopened-bottle count means zero, in both forms and logging.
- Status tracking uses manual Unknown, Have, Low, or Out availability. Logging a drink will not decrement or automatically change qualitative status, and no automatic Low threshold is selected. Qualitative availability does not prove a sufficient quantity for any number of servings.
- Only the selected mode's stock fields are authoritative. Mode changes explicitly initialize the newly selected representation. The bottle creation form defaults to 100% full when full volume is entered, and offers percent-full estimates or direct mL entry for existing stock. It shows the resulting mL and stores only that quantity. A blank amount means none, the same as zero (decided 2026-11-06: migrated notes left blanks where the old views meant not owned, and nothing used blank as "not measured"). Changing tracking modes initializes measured amounts and the unopened-bottle count to zero, and availability to Unknown. Unknown stock is only availability marked Unknown, or no tracking mode.
- `cc-shopping-list` is an optional boolean on ingredient types, bottles, and other-stock sources, defaulting to false. It expresses explicit purchase intent independently of availability. Flags do not propagate through classification links, and the shopping list includes every explicitly marked resource.
- `cc-last-purchase-price` is an optional nonnegative number on bottles and other-stock sources. Missing or null means unknown; zero is valid. Preserve the existing numeric-price convention without currency symbols or inferred conversions. Price history and per-mL costing are not part of this change.

## Review of the default hierarchy

The optional-parent direction is agreed; individual ingredient classifications remain open to review. The current [starter hierarchy](starter-hierarchy.md) lists the default types and their proposed groupings.

The optional-parent review established these default groupings:

- Remove the Mixer and Pantry catch-all categories.
- Replace the Bitters category plus Cocktail Bitters family with a single parentless Bitters family.
- Keep Carbonated Mixer as a useful family without creating a broader Mixer category.
- Remove the Dairy and Egg and Garnish and Seasoning families; their types stand on their own in this pass.

The remaining branches retain their previous draft classifications for later focused review. This round does not approve all those classifications or change the ingredient identities.

## Adoption and logging decisions

Agreed on 2026-11-03 while scoping [roadmap](roadmap.md) Phase 1.

- **Match the starter.** The `knowledge` vault adopts the starter classification wherever the two overlap, rather than preserving its own types locally. Bottle-level decisions and meaning-changing recipe links are settled before migration. Types the starter does not cover become local types in the plugin schema, under an existing starter family where one fits.
- **One-off migration.** The `knowledge` vault is migrated by a one-off script with a dry-run report, rehearsed on a copy first. A general in-plugin adoption flow is not planned; reusable building blocks may be offered later.
- **Plugin link style.** Migration rewrites every ingredient link to the generated style (vault-relative path with display text), replacing the vault's bare-link convention.
- **Logging entry point.** **Log this cocktail** is an Obsidian command on the recipe note. It runs on desktop and mobile (mobile enabled 2026-11-05, before a mobile layout pass).
- **No hard-coded substitution rules.** The vault skill's always-ask-for-Green-Chartreuse rule is not built in. Instead, every counted ingredient line in the review can be changed before apply:
    - The picker first lists owned bottles that fit the line in the hierarchy: a type's bottles; any bottle of a type in a referenced family; or a referenced bottle plus the other bottles of its type.
    - A final **Other bottle…** option searches every bottle in the cabinet for exceptional substitutions.
    - A line with one candidate, or naming a specific owned bottle, is pre-selected. A line with several candidates starts unselected, and apply is disabled until each such line is chosen.
    - The preview and shortfall check follow the current selections; apply writes exactly what is shown. Recording substitutions is out of scope for now.
- **Stock editing deferred.** Bottle creation plus hand edits of stock fields are enough to start real use. Superseded by [editing stock](#editing-stock).

### Logging implementation

Logging is used several times a week, so its text is terse: the title is “Log <recipe>”, sections are Used, Stock, Not subtracted, and the daily-note toggle, empty sections are hidden, and the save action is **Log**. Errors name the bottle and the problem in a few words (“Campari: 15 mL short.”) rather than exposing property keys. Every picker also offers **Don’t subtract**, the default for a line nothing in the cabinet stocks (fresh juice, for example), so untracked ingredients never block logging.

**Log this cocktail** is available on active cabinet recipe notes, desktop and mobile. The review starts at one serving with a numeric control. When a line gives both ounces and mL, as in `2 oz (60 ml)`, `¼ oz (7.5 ml)`, or `2 oz / 60 ml`, the **Amounts given in oz and mL** setting picks which stated amount is the pour (US fluid ounces by default), without converting the other; ranges and qualified quantities remain unmeasured. The initial picker includes matching measured other-stock sources through `cc-provides`, alongside bottles. Every link on one ingredient line is a possible alternative for that single pour, including parenthetical links. Status-only requirements are listed as not drawn down; selecting a status-tracked bottle through the exception picker also leaves it unchanged.

Daily notes uses the core plugin’s configured folder, format, and native template-based creation. One serving writes `Made a/an [[path|Recipe]].`; other positive serving counts write `Made 2 servings of [[path|Recipe]].` Existing Made entries turn the daily-entry control off by default, with an explicit option for another round. Disabled Daily notes or unusable configuration blocks daily-entry apply; clearing the control permits inventory-only changes.

Usage is recorded on every log (added 2026-11-06): `cc-last-used` on each source written (in the same frontmatter write as its stock change), on each selected status-tracked source, and on the one source a skipped line clearly uses (a named bottle or other stock, or the only source fitting the line), never on a line set to **Don't subtract**; and `cc-last-made` and `cc-times-made` (+1 per log, whatever the servings) on the recipe. Dates come from the review's daily-note date, which defaults to today and can be set to an earlier day in the log dialog (added 2026-11-07, for drinks remembered the next day; future dates are refused), and never move backward, so logging an older drink doesn't lower a later last-used or last-made date. These writes are bookkeeping: a failure is named in the notice and doesn't undo the log. The recipe write doesn't affect the stale-recipe check, which runs before any write. Ingredient last-used dates aren't backfilled from daily notes (half of past drinks name only a type with several bottles); recipe dates and counts were backfilled for the `knowledge` vault once.

Preview and apply use fresh note properties, including immediately after a write while Obsidian’s metadata cache is rebuilding. Apply preflights all selected stock before writing and checks each source again inside `processFrontMatter`, changing only applicable stock fields. Shortfalls prevent all writes. Stock writes precede the daily entry. An I/O failure after writes begin reports confirmed changes and disables further logging in that review; **Undo last log** recovers it (below).

### Undoing a log

Agreed on 2026-11-13 in place of retry protection alone: logging already preflights and stops cleanly, so a recovery tool earns its place only if it also covers ordinary mistakes (the wrong servings, the wrong bottle).

- **Record.** Each log keeps a record in the plugin's data: every property it changed on each note, before and after, and the daily entry it appended. The record is saved before the first write with the planned stock changes, then each write replaces them with what it actually changed, including `cc-last-used`, `cc-last-made`, and `cc-times-made`. A log whose first write fails saves nothing, so its record is dropped. The last 10 records are kept; settings synced from another device replace the loaded ones (`onExternalSettingsChange`).
- **Undo by value.** Undo compares each property with the record, not with progress markers: a value still at the log's result is put back, one still at its old value was never saved and is skipped, and anything else changed since. This makes a partly failed log, and a partly failed undo, safe to undo again.
- **Changed stock blocks.** A stock amount changed since (another log, **Edit stock**, a hand edit) blocks the whole undo, which would otherwise erase that change; the review says which note and its current value. Changed dates and counts are kept as they are and listed.
- **Review, then apply what was shown.** **Undo last log** (and the **Undo** link in the logging notice) opens a review of what it puts back. Apply re-plans from fresh properties, and any difference from the review refreshes it instead of writing; each write checks its values again inside `processFrontMatter`.
- **Daily entry.** The last exact copy of the appended entry (one line, or a one-off's header and list) is removed; if it's gone, the notice says so. A daily note the log created is left in place.
- **Order.** Undo walks back from the latest log. Undoing an older log first isn't offered.

### One-off drinks

Agreed on 2026-11-10 and built the same day. Logging needed a recipe note, so a drink made up on the spot meant inventing a name and keeping a file for something not yet worth keeping. That reluctance is likely shared, and an unlogged drink leaves stock wrong.

- **Recorded in the daily note only.** No file is created. The entry is the header `Made a one-off (Name):`, or `Made 2 servings of a one-off:`, then the ingredient lines per serving as a list, links included. The name is optional, one line, without square brackets. With **Record alcohol in daily notes** on, the header ends with the standard drinks before its colon: `Made a one-off (Name) (≈ 1.6 drinks):`. A name can't itself read as drinks text. A draft recipe in a holding folder was considered and rejected: it is still a file to name and clean up.
- **Same review as a recipe.** **Log a one-off** asks for ingredients with the recipe form's ingredient rows, then an optional name (below them and starting focus in the first amount, decided 2026-11-10 after the name field first in line read as expected), then **Review** opens the logging dialog on those lines, read exactly as a recipe's: pickers, splits, **Don't subtract**, stock preview, date, and **Last used**. **Edit ingredients** goes back with everything kept. Lines can't be linked in place (**Link…** writes into a recipe; a one-off has none), so link them on the ingredients step. Nothing counts as a duplicate: the same one-off can be made twice in a day.
- **Riffs.** **Riff on this cocktail**, on a recipe note, starts the same flow from that recipe's ingredient lines. The header adds `, a riff on [[Recipe]]`. A riff doesn't count as making the recipe: it isn't a duplicate for **Log this cocktail**, and the recipe's last made and times made don't change.
- **Promotion from the daily note.** **Save one-off as recipe**, on the note holding the entry, reads the one-off back (picking one if there are several) and opens the recipe review with its name and ingredients, and for a riff a description naming the recipe. Once created, the header becomes an ordinary made line, `Made a [[Recipe]]:` (or `Made a [[Recipe]] (≈ 1.6 drinks):`), keeping the poured list, and the recipe counts as made once on that note's day (from the Daily notes format). Only the chosen entry is relinked; earlier makes of the same one-off stay one-offs. A header changed since it was read is left alone and the notice says so. Deciding at log time ("save as recipe" in the log dialog) was considered; promotion later covers it without a decision in the moment.

## Homemade stock

Agreed on 2026-11-04, after managing syrups in the dev vault meant an other-stock note named the same as its type (Simple Syrup (1 to 1) providing Simple Syrup (1 to 1), before the ratio names below).

- **One rule, no stocked types.** Types stay what recipes call for; stock is always a bottle or other-stock source under a type. Letting a type carry its own stock was considered and rejected: people buy some syrups and make others, and switch over time (bought simple syrup first, homemade later), so stock on the type would mean moving it between note kinds, and a type could hold stock and have bottles at once. Everyday ingredients with no brand or batch to tell apart are [kitchen staples](#kitchen-staples), agreed later.
- **The collision is a naming problem.** Bought products have their own names (a brand); only homemade sources end up named after their type. The Homemade syrup and Prepared juice forms default the name to "House <type>", for example House Simple Syrup (1:1) or House Lime Juice, and the user can change it.
- **Ratio names for syrups.** Decided the same day: sugar syrup types are named by ratio, Simple Syrup (1:1), Simple Syrup (2:1), and Demerara Syrup (2:1), with the everyday names (Simple Syrup, Rich Simple Syrup, Demerara Syrup, Rich Demerara Syrup) as aliases. "Rich" isn't a fixed ratio, and the type name mostly appears in pickers, stock tables, and the shopping list, where the ratio matters; recipes keep their own wording as link text. The filename rule spells the ratio out (`Simple Syrup (2 to 1).md`), exactly as accents fold, so filenames and catalog IDs are unchanged. The earlier "(2 to 1)" names were a filename workaround from before names and filenames were separate.
- **Add stock from the type note.** Two commands on a type note, **Add a bottle of this type** and **Add other stock for this type**, open the matching form with the type or Provides filled in, so the separate source note rarely needs opening; the type's Stock section already shows it. Two commands rather than a guess, since most types can be either (decided 2026-11-04).
- **The suggestion yields to typing.** The House name follows the form and first provided type while the name is blank or still the suggestion; anything typed is kept.
- **Worked example.** Decided 2026-11-04. A new cabinet gets Limes and Lemons (availability, providing the juice and peel types), House Simple Syrup (1:1) (mL), and a Daiquiri and Whiskey Sour, so a drink can be logged on day one. Stock starts Unknown rather than with sample amounts: the first log asks for the syrup amount or **Don't subtract**, and the Cocktail Cabinet note says to set it. Examples are the user's notes, so setup adds them only when it creates the Cocktail Cabinet note and never restores a deleted one; a file already at an example path is kept rather than blocking setup. Each has a catalog ID (`ingredient/Limes`, `recipe/Daiquiri`) listed in `STARTER_EXAMPLES`, for the migration to recognize.

## Kitchen staples

Agreed on 2026-11-08. Creation, the starter, views, and unmeasured-line review built 2026-11-09. [Homemade stock](#homemade-stock) assumes the type already exists. Adding saline solution, where neither exists, took a type, then a source, then a name and Form that don't fit, and left two notes for something nobody thinks of as two things. The extra steps at creation are the worse problem, because they can make someone give up on the cabinet; the second note is a smaller, lasting mismatch with how people think about salt or mint.

- **What a staple is.** An everyday ingredient tracked as itself: other stock that provides no type, because it is the ingredient. The test: if you'd care which brand or batch, make a type; otherwise add a staple. The buy-versus-make argument for keeping types and stock apart doesn't apply here, since nobody tracks which eggs or mint they bought, only Have, Low, or Out.
- **No new note kind.** A staple is `cc-kind: ingredient` with no `cc-provides`, status tracking, and a new `cc-form` value, `Kitchen staple`. Recipes link it directly, as they already can a bottle or other stock, and keep their wording as link text. Logging already matches a directly linked source exactly. If someone later starts caring about the distinction, they add a type, set Provides, and repoint recipes.
- **One note per ingredient.** One Mint, one Salt, and Salt separate from Saline Solution. Saline Solution's note describes it as 20%; another strength is the user's own staple, such as Saline Solution (25%).
- **Eggs are a source.** One Eggs note provides the Whole Egg and Egg White types, the same shape as Limes providing juice and peel: one status for one carton.
- **Creation.** Choosing the Kitchen staple form in **Add other stock** hides Provides, leaving a name and availability. It was also its own command, **Add kitchen staple**, because nobody thinks of salt as "other stock"; that was folded into the form on 2026-11-24 (see [command scope](#command-scope)), since the two did the same thing and the form's first choice says it.
- **Starter.** Common staples ship at Unknown, which delays the need to create one and shows how they're meant to be used: Salt, Saline Solution, Mint, Water, Heavy Cream, Milk, Cinnamon Sticks, and Whole Nutmeg, in the catalog like reference bottles, plus Eggs (`Fresh ingredient`). Salt, Mint, Heavy Cream, and Milk were types and converted. Soda Water and Cocktail Cherry stay types (decided 2026-11-09): brand matters for both. Setup keeps a note already at a starter staple's path, since someone may have added their own first.
- **Considered and rejected.** A catch-all parent type (Kitchen, Grocery): catch-all behavior applies only between bottles, so the flag would do nothing; no recipe would ever call for the type, which breaks "types are what recipes call for"; Same type would list salt beside mint; and the difficulty naming it reflects that these share no recipe role. Stock on types: workable for staples, but it needs new behavior everywhere, while other stock already has status tracking, the shopping list, and logging. One form that creates a type and a source: it removes the steps but keeps the second note.
- **Views.** Built 2026-11-09. Staples scatter the collection further and wouldn't appear in Ingredient types, and the starter's shape is how people learn the system, so: a **Browse** tab in Ingredient types grouped by category and family ("Spirit › Rum"), with groups for standalone types and kitchen staples and a Have column; a **Kitchen staples** tab in Other stock (name, availability, last used, shopping list), which doubles as onboarding, walking the kitchen and marking what's there; and a new **In stock** view of bottles and other stock together. Restock's Unknown tab leaves staples out, since they have their own. The Cocktail Cabinet note gets a Kitchen staples section and a short "start here" order.
- **View behavior.** The existing default tabs keep their filters, columns, and labels. Browse includes types and kitchen staples, with groups named by category and family using proper names (for example Spirit › Rum), by family alone when it has no category, or Standalone types and Kitchen staples. Have links the type's stocked sources, or the staple itself when Have or Low. The Kitchen staples tab keeps the shared Availability (status mode) label from Other stock. In stock combines bottles and other stock: Have or Low, positive open mL, unopened bottles, or remaining mL; Unknown and blank amounts do not count. Blank numbers are guarded before comparisons, including the shared shopping-list Have expression. Only Restock's Unknown excludes staples, with a kind-first test so bottles without `cc-form` remain included. A **Least used** tab (added 2026-11-13) lists stocked bottles and other stock, staples excepted, by Last used, oldest first, with never-used first: a nudge to use up what's been sitting. It sorts on a formula showing the date or “(never)”, since a view sorts only on what it shows and missing dates would sort last.
- **Existing Cocktail Cabinet note hand edit.** Superseded 2026-11-21: the note is now managed, and `knowledge`'s was replaced with the managed version. Setup preserved `Cocktails/Cocktail Cabinet.md`. For `knowledge`, manually add the following before Your collection and before Other stock respectively (adjust to the note's heading levels), add `[[Cocktails/Views/In stock.base|In stock]]` to the collection links, and mention the Browse tab and its Have column in the Ingredient types description. This implementation does not edit `knowledge`.

    1. Open Other stock → Kitchen staples, walk through your kitchen, and set availability on the staples you have.
    2. Set the stock on your bottles and other ingredients. Ingredient types → Browse shows what you have under each type.

- **Views verification.** Desktop dev-vault CLI queries on 2026-11-09 checked Browse's Have links and all four grouping cases (using a temporary diagnostic Base to expose the group formula), Kitchen staples columns, combined In stock, blank amounts, sealed-only and open-only bottles, Unknown bottles without Form, and Low/Out staples remaining in Restock. Temporary fixtures were removed. Mobile layout and editing through the tables were not checked.
- **Reviewing unmeasured lines.** Built 2026-11-09: **Review unlinked ingredients** includes unmeasured lines whose wording exactly matches an existing ingredient note's name or alias after normalization with `ingredientKey` (case, accents, spacing, and curly apostrophes). This applies to every ingredient note, independently of the staple form. Leading amounts such as "2 drops", "1 sprig", and "pinch of" are kept outside the link; "mint leaves" can match an alias. Unmatched unmeasured lines stay out. Lines marked as garnish ("Garnish:", "to garnish") stay out by default; **Show garnishes** includes those matching a name or alias, grouped with the same wording elsewhere; the marker stays outside the link. With no **Keep as text**, anything never linked would otherwise stay listed forever, and many home bartenders skip garnishes that don't affect flavor. Unmarked garnishes such as "1 sprig mint" are treated like other unmeasured lines. Measured lines keep their existing behavior, and linking an unmeasured line does not make logging subtract it. ## Editing stock

Agreed on 2026-11-04 as the first Phase 2 item, replacing hand edits of `cc-open-ml`, `cc-unopened`, `cc-remaining-ml`, and `cc-availability`.

- **One form with shortcuts.** **Edit stock** is a command on bottle and other-stock notes, desktop and mobile. It opens a form filled from the note's current stock (read from the file, not the metadata cache), shows Now and After, and saves only what changed.
- **Bought more** adds one sealed bottle per press (volume-tracked bottles) or sets Have (availability), and switches the shopping-list flag off; the price field is right there to update. For other stock tracked in mL it only clears the flag, and the new amount is typed. Automatic flag clearing applies only to this explicit purchase action, not to stock changes in general.
- **Finished** empties the open bottle (0 mL open; sealed bottles stay), sets other stock to 0 mL, or sets Out.
- **No Open next bottle.** Considered and dropped: logging already opens a sealed bottle when the open one runs out, so 0 mL open with a sealed spare behaves the same, and opening early raised an unclear question about the leftover.
- **Levels.** The open bottle starts in percent full when the bottle size is known, else mL. An untouched value keeps the exact saved mL, so opening and saving never rounds stock.
- **Mode switches.** A new mode starts empty (Unknown availability, blank amounts, which read as 0) and is never converted from the old one; switching back to the saved mode restores its values. Saving a switch removes the old mode's stock fields.
- **Stale protection.** Save re-reads the note inside `processFrontMatter` and refuses, changing nothing, if stock, price, or flag changed since the form opened. Bottle size and ABV stay in Properties.
- **No check dates.** Tried and dropped 2026-11-06: a `cc-stock-checked` date written on every save, and a list ordered by oldest check. Stock doesn't drift on its own (Out stays Out until a purchase), so re-confirming settled stock was busywork, worst for bottles bought once and not rebought.
- **Fix as you go.** Added 2026-11-06. Stock is often out of date because a purchase or an unlogged drink wasn't recorded, so the logging modal opens **Edit stock** in place: a button on each source whose stock is short, and a gauge button on each Stock row. Saving re-reads the review and keeps selections. Looking over stock is the **Restock** Base, for the job of choosing what to buy: Running low (Low, or the last bottle at or under the percent-full setting, default 10%, or the mL setting, default 70, without a bottle size and for other stock), Out (Out, or nothing above 0, blank counting as 0; by name, since modified dates are unreliable under sync and Git), and Unknown (Unknown or missing availability, or no tracking mode), each with the shopping-list checkbox. Nothing asks to dismiss an old bottle; nothing marks a bottle as not to be rebought, which would go stale when you change your mind.

## Recording purchases

Agreed on 2026-11-06. Restock helps choose what to buy; missed purchases are the main reason stock is wrong, so recording a trip is one form rather than **Bought more** per note.

- **Where.** **Record purchases**: a header button on the Shopping list note (and its menu), and a command that works from anywhere.
- **Layout.** Revised 2026-11-06 after the first version bounced: rows grew when checked and the centered modal re-centered. The modal sits near the top and only the list scrolls. Sections are "From your shopping list" and "Also bought" rather than kinds. On narrow screens the fields wrap under the name.

No group headings: tracking modes aren't how people think about a trip. Each records `cc-last-purchased`, never moved backward; **Bought more** sets it too. Only the last date and price are kept, no history.

## Renaming

Built on 2026-11-05 as the Phase 2 rename, replacing the three hand edits a recipe rename took.

- **One command for every cabinet note.** **Rename cabinet note** works on recipes, bottles, other stock, and every hierarchy level, desktop and mobile. The form takes the new proper name and shows the resulting filename; the note stays in its folder. A filename already taken, ignoring case, stops it before anything is written.
- **What follows.** `cc-name` takes the new name. The first `# ` heading follows if it showed the old name or filename; any other heading is left and the notice says so. The old name leaves `aliases` unless **Keep the old name as an alias** is on; the new name is added when it differs from its filename, as at creation. `cc-catalog-id` is unchanged, so setup still recognizes a renamed starter note.
- **Links.** The file moves through Obsidian, which updates links according to the vault's settings. Then every note that linked to it, daily notes included, is checked: display text showing the old name, old filename, or the new filename (which Obsidian's own updating writes over old-filename text) becomes the new proper name. Other display text is recipe wording and stays. Links that no longer resolve, because automatic link updating is off, are pointed at the new path. A note whose links all used full paths keeps full paths, even when Obsidian's link format would shorten them. Property links (`cc-type`, `cc-provides`, and the rest) are updated through the frontmatter API.
- **Stale protection.** Save refuses, changing nothing, if `cc-name` changed after the form opened. Link failures after the move are listed in the notice rather than undoing the rename.
- **Renames made in Obsidian.** Built 2026-11-24. Renaming a cabinet note's file through Obsidian (its title or the file explorer) is followed: once Obsidian has had time to update links (1.5 s), `cc-name` becomes the new filename, the old name leaves `aliases`, the heading follows, and link text showing the old name or filename becomes the new name. Obsidian has already repointed links in its own format, so nothing is repointed, except that notes under the cabinet folder get their full-path links back. Nothing happens for a folder move, for the plugin's own rename (its `cc-name` already matches), or for the plugin's own pages. A filename can't hold every character a proper name can (`Tuxedo #2` is `Tuxedo No 2.md`), so such a name still needs **Rename cabinet note**; it stays in the file menu beside Obsidian's **Rename…** so it's found.
- **Not covered.** Markdown-style `[text](path.md)` links get only Obsidian's path update.

## Command scope

Decided 2026-11-24, from a review of every command, menu item, and view.

- **Listed only where it applies.** A command that can only fail somewhere isn't listed there. **Convert note to recipe** (formerly **Enhance as cocktail recipe**) is listed only on notes without `cc-kind`; cabinet recipes have **Edit cabinet note** and **Tidy ingredient lines**. **Save one-off as recipe** is listed only on daily notes, as the Daily notes core plugin names them, and the right-click menu on a one-off's header line saves that one. **Insert ingredient link** is listed only in recipes, and its right-click item too. **Set up cabinet** is hidden once the cabinet is set up (the settings tab keeps the button), and **Undo last log** while there's nothing to undo. **Review cabinet updates** stays listed: knowing whether anything waits takes a vault scan, and an empty review says the notes are current.
- **Log a one-off stays everywhere.** Logging a recipe starts from the recipe; a drink with no recipe has no note to start from, so it's a top-level command.
- **Commands, not only menu items.** An editor action that's also a command can go on the mobile editing toolbar, which takes only commands. That's why **Insert ingredient link** stays a command, narrowed rather than removed.
- **Header buttons.** Recipes show **Log this cocktail**, bottles and other stock **Edit stock**, and every note with editable fields **Edit cabinet note**. Having both edits on a bottle was considered clutter, but **Edit cabinet note** sits beside Obsidian's own editing on purpose: hidden in a menu, people would edit properties by hand instead.
- **Fewer creation commands.** **Add ingredient type** has a **Level** choice for a family or category, which are rarely added; switching keeps the name and description. Kitchen staples are a form in **Add other stock**. **Create a cocktail recipe** became **Add recipe**, so typing "add" finds every creation command. Command IDs changed to match (`add-recipe`, `convert-note-to-recipe`, `add-bottle`, `add-other-stock`, `add-ingredient-type`, `tidy-ingredient-lines`): the plugin isn't released and has no hotkeys to keep.
- **On a type note, two add items stay.** **Add a bottle of this type** and **Add other stock for this type** open different forms, and a type rarely holds both.
- **Tasting notes removed.** See [tasting notes](#tasting-notes).
- **Smaller changes.** **Tidy this recipe** is **Tidy ingredient lines**, saying what it changes. The Shopping list note links **What should I buy?** beside Restock. Families and categories share one Base, **Ingredient families and categories**, with a view each; syncing moves the two retired Bases to the trash. The guide's list of views leaves out Related, which only supplies the sections inside notes. Settings are grouped under Stock, Recipes, Alcohol estimates, and Maintenance.

## Recipe tags, rating, and duplicates

Built on 2026-11-13, finishing the recipe review's Phase 4 item, and revised the same day after discussing what the plugin should categorize.

- **No method category.** A first version hard-coded four prep tags (`shaken`, `stirred`, `built`, `blended`) and picked one from the method text. It was removed: technique is a poor way to group drinks. The same drink is stirred or built depending on the author (an Old Fashioned), and a built Caipirinha drinks like a Daiquiri, not a Manhattan. What “stirred and boozy” vs “shaken with juice” really separates is the ingredients. Swizzled and thrown were rejected for the same reason. No `cc-method` property either.
- **Computed facts instead.** The plugin should offer only what it can read from linked ingredients: whether a recipe has citrus or juice, dairy or egg, or something sparkling, with “spirit-forward” as none of these. These belong with the [alcohol estimate](alcohol-estimate.md), which reads the same lines and stores results the same way. Not built yet.
- **Dilution is inferred, not stored.** The estimate needs dilution, so it assumes shaken-style dilution for recipes with juice, dairy, or egg and stirred-style otherwise. Blending or crushed ice in the Method text means more, and builds and long drinks are flagged as rougher estimates.
- **Tags are the user's.** The plugin defines no tags. The Tags row offers every tag already on a cabinet recipe (the `tags` property or inline), most used first, then the recipe's own, and a field adds any valid tag. A new cabinet starts with no buttons. The starter ships no tags, because any it shipped would be the plugin choosing a categorization; the Cocktail Cabinet note and README explain them instead.
- **Native tags, in the `tags` property.** Native tags work with Obsidian's tag pane, search, `#` autocomplete, and Bases (`file.hasTag`); a `cc-tags` property would be plain text to Obsidian. Pollution of the vault's tag namespace is small: the form counts only cabinet recipes, and anyone wanting separation can nest tags (`#cocktail/tiki`). The property replaces inline tags at the end of Tasting Notes, which looked tidy for hand editing but got messy. Create and Enhance move trailing inline tags into it; **Edit cabinet note** moves them on any save, removing Tasting Notes if nothing else is left there. An order-only change to the property isn't written.
- **Tasting Notes leave the forms.** They aren't a form field anymore. Text a source or an existing note has is kept as written, and a recipe without any gets no Tasting Notes heading. Links in Tasting Notes made recipes show up under ingredients they don't use (see the roadmap's ingredient-only links), and impressions change from one drink to the next. They fit better in the daily note beside the drink's “Made …” line, where the recipe's backlinks show them.
- **Rating.** The same dropdown as **Edit cabinet note**, filled from the pasted or enhanced note's rating. A saved value that can't be read stays when **Keep as written** is chosen.
- **Duplicates warn, never block.** As the name is typed, a recipe whose name, filename, or alias matches it loosely (accents, case, punctuation, `&` as “and”, and a leading “The” ignored) is named under the field, with a link that opens it in a new tab. Different drinks can share a name, so saving is still allowed; a filename clash is refused as before.

## Tasting notes

Built on 2026-11-13, after Tasting Notes left the recipe forms; removed 2026-11-24 (see [command scope](#command-scope)).

**Add tasting note** wrote `Tasting note on [[Recipe]]: …` under the day's “Made …” line in the daily note, so the recipe's backlinks collected a dated history. Logging already writes that line with the recipe's link, so typing after it gives the same result, and lasting notes belong in the recipe's Tasting Notes section. Lines it wrote still never count as a log for the duplicate check.

## Navigation in notes

Agreed on 2026-11-04, after testing logging in the dev vault showed that moving around the hierarchy was missing.

- **Embedded core Bases, not a plugin-rendered block.** One shared `Views/Related.base` holds a view per section; each note embeds the views it needs with one line, and `this` identifies the note. It renders with the plugin disabled and stays sortable and editable. Verified on desktop Obsidian 1.14.5: formulas can follow links across notes (`link(value).asFile().properties`), so a Base can climb bottle → type → family → category.
- **Sections by kind.** Category: Families, Recipes. Family: Types, Stock, Recipes. Type: Stock, Recipes. Bottle and other stock: Same type, Recipes. No parent section; the properties panel already shows the parent. Families and Types are list views. Recipes, Stock, and Same type are tables; a Recipes table lines up the star ratings for scanning. Stock rows show "N mL", or the availability; a bottle shows the open bottle as percent of its size with mL after it, "88% (660 mL)" (mL alone without a bottle size, "<1%" below one percent), then ", M unopened" only when there are some, and "None" when neither is positive. Percent leads because it is how a shelf is read and compares across bottle sizes; mL stays the stored amount. The Edit stock and logging summaries use the same wording. A missing open amount reads as none open in this display (decided 2026-11-04); logging still treats it as unknown. Recipes show their rating as stars and sort highest first, unrated last.
- **Recipes split in two** (decided 2026-11-06). One table grouped on a formula: "Calls for <this note>" (recipes that link it or, on a type, family, or category, anything under it), then "Can fill" (recipes calling for something broader, or, on a bottle of an ordinary type, naming another bottle of its type). A grouped table was chosen over two embedded views because existing notes keep their single `#Recipes` embed. Bases orders groups by their text, so the labels are chosen to sort that way; the group property's label is blank so a heading shows only the group.
- **Plugin-owned**, like every view in `Views/`. Sort, filter, and column changes made in any embed are saved to this shared file and affect every note; that is how core Bases embeds work.
- **Custom view later.** A plugin-registered Bases view could be read-only, offer actions (Log, Edit stock), and show which recipes you can make now, but renders nothing with the plugin off. Revisit once availability queries exist.
- **Ratings are numbers.** `rating` is an integer 1–5, decided the same day; stars are a display formula. The `knowledge` migration converts its ⭐️ strings.
- **Recipes rule.** It mirrors `relatedTargets`: recipes that link this note or anything under it, anything above it, or, for a bottle, another bottle of its type. It reads each recipe's `cc-ingredients` (below), so only Ingredients links count; a recipe without the property falls back to every link in the note.
- **Ingredient links property** (decided 2026-11-13). Counting every link (`file.links`) listed recipes under ingredients they only mention, in Description, Method, or Tasting Notes; 16 `knowledge` recipes had links in Tasting Notes alone. Bases can't scope links to a section, so the plugin keeps `cc-ingredients` on each recipe: the notes its Ingredients section links, as path links with the note's name, or as written when nothing matches yet. It is derived, never edited by hand: the section stays the source. Since the alcohol estimate's slice 3, the same sync (`RecipeSync`) also writes the estimate properties. The plugin updates it from the metadata cache, without reading files, when a recipe has been unchanged for two seconds (so typing isn't interrupted), and checks every recipe five seconds after startup for edits made while Obsidian was closed. It writes only when the set of linked notes differs, so its own write doesn't loop and two synced devices write the same thing. An empty list means no ingredient links and stops the fallback. The section runs from the Ingredients heading to the next heading at its level or higher, so a Garnish subheading's links count; embeds don't. Renames update the property through Obsidian's own link updating, and the next sync corrects anything it misses. Views still render with the plugin off, from the last saved property.
- **Catalog updates** (built 2026-11-22, [ownership](ownership.md) slice 3) replace one-off passes such as the typical-ABV pass: starter notes found by `cc-catalog-id` get each untouched field from the catalog on the first startup after a catalog change, and on **Refresh cabinet notes**.
- **Kept present** (built 2026-11-21, [ownership](ownership.md) slice 2; replacing "generated, not migrated"). New notes and the starter get the embeds. When a release changes the sections by kind (the plugin records the rules it last applied), and on **Refresh cabinet notes**, each resource note gets any section its kind shows and it lacks, including Subtypes on a type with subtypes. A missing embed goes before the next present section in the kind's order, else after the previous one, else at the end; embeds already there are never removed or moved, and short links such as `![[Related#Stock]]` count as present. A removed section comes back, like a derived property.
- **Single parents.** `cc-family` and `cc-category` became single links on the same day, matching `cc-type`, which also keeps the formulas simple.

## Catch-all types

Decided 2026-11-06. Some types group products without close substitutes: Amaro, Herbal Liqueur, Spice Liqueur, Flavored Rum, Specialty Bitters. `cc-catch-all: true` marks one, set in the type's creation and edit forms; the starter marks those five. A catch-all is a lesser type: its bottles are likely substitutes for each other, not assumed ones.

- **Logging.** A line naming a bottle of a catch-all type offers that bottle, then the other stocked bottles of the type under an "Other Amaro" heading in the picker. They are never selected for you: when the named bottle is out, the line starts unselected, and **Log** waits for a choice (another amaro, **Other bottle…**, or **Don't subtract**). A line naming the type itself ("½ oz amaro") accepts any of its bottles, like a family, with the usual single-candidate preselection.
- **Navigation.** A bottle's Recipes leave out recipes naming another bottle of a catch-all type; recipes calling for the type itself, or anything broader, stay under Can fill. Same type stays: it's where to look for a substitute. The type's own Stock and Recipes are unchanged.
- **Not affected.** Shopping list and Record purchases type rows, and Stock sections.

## Subtypes

Approved and built 2026-11-13. Bonded bourbon and rye showed the gap: cocktail apps such as BevNap keep them distinct, and recipes that call for bonded deserve a 50% estimate and a strict match. But a separate type would stop bonded bottles from filling the many recipes that just say bourbon, and [types are not used for substitution](#classification-principles). A subtype is the narrower kind of a type. It always fills its parent's lines, never the reverse.

- **The model.** An optional level below type: category → family → type → subtype. A subtype is a type note (`cc-kind: type`) whose single parent is `cc-type`, linking its type, in place of `cc-family`. One level only: a subtype has no subtypes, so the Bases keep a fixed depth. Bottles and other stock link a type or a subtype through `cc-type` as now.
- **Matching.** A line naming a type accepts the type's bottles and its subtypes' bottles, as a family link accepts every type in it. A line naming a subtype accepts only the subtype's bottles. The parent's other bottles are offered as likely substitutes, as with [catch-all types](#catch-all-types), and are not counted as available.
- **Logging.** A type line's picker lists the type's own bottles, then each subtype's under its name. A subtype line lists the subtype's bottles, then the parent's other bottles under an "Other Bourbon" heading, never selected for you.
- **Navigation.** A type with subtypes gets a Subtypes section, ahead of its others: the starter writes it, and creating a subtype or choosing **Subtype of** in **Edit cabinet note** adds it to the type's note. Other types don't show an empty one. Its Stock includes its subtypes' bottles, and its Recipes include recipes calling for a subtype, as a family's do for its types. A subtype bottle serves recipes naming any bottle of its parent type; a parent-type bottle doesn't serve recipes naming a subtype bottle. Same type reaches both ways, as answered below.
- **Estimates.** A subtype has its own typical ABV (Bonded Bourbon 50%); the parent keeps its standard value (Bourbon 43%). A subtype line uses the subtype's in-stock bottles, then its typical value, then bottles of it you've had, then its type's estimate.
- **Forms.** Add ingredient type and Edit cabinet note offer **Subtype of (optional)**, listing types that aren't subtypes; a type with subtypes isn't offered the field. A subtype's family is its type's, so saving one with both is refused.
- **Bases.** Ingredient types shows a Subtype of column. Browse groups a subtype under its type's family; its Have lists only the subtype's own stock.
- **Starter subtypes.** Bonded Bourbon and Bonded Rye; Navy Strength Gin under London Dry Gin; Aged Overproof Jamaican Rum under Aged Jamaican Rum, since Smith & Cross is only lightly aged and fits Mai Tais. Apple Brandy becomes the broad type in the Brandy family, with Bonded Apple Brandy, Applejack, and Calvados as its subtypes, replacing Apple Brandy Family; family links to it become type links with the same meaning.

**Spike** (before building; its fixes are in). Tried in Cocktail Cabinet Dev on 2026-11-13 with synthetic notes, adding one level of depth to the Related Base's formulas (`up4`, `thisUp4`, `linkedUp4`). The formulas already follow every parent key, so a subtype linking its type through `cc-type` needed nothing else to roll up:

- **Worked.** The type's and family's Stock list subtype bottles. The type's Recipes list subtype recipes under "Calls for Bourbon". The subtype's Recipes show its own recipes as "Calls for" and its parent's and family's recipes as "Can fill". A subtype bottle can fill plain bourbon and whiskey lines.
- **To fix.** A plain bourbon bottle listed a bonded-only recipe under Can fill: the same-type rule reads the parent of every linked note, so a subtype link looked like a bottle of the parent type. It should read only linked bottles. A bonded bottle missed recipes naming a plain bourbon bottle: its swap types should include its parent type.
- **To build.** A "Subtypes" view label: the spike reused Types. Existing type notes have no Subtypes embed, since setup doesn't edit notes; adding the embed to the parent when a subtype is created is one option. The Ingredient types and Browse Bases group by family, so subtypes would show up as standalone types there.
- **Code.** The availability rule in `relatedTargets`, the logging picker, the estimate's bottle medians, recipe sync, the type creation and edit forms (choosing a parent type in place of a family), `catalogDraft`'s parent mapping, and the knowledge migration.

Answered 2026-11-13:

- **Estimate order.** A line naming the type uses the type's own in-stock bottles first, then its subtypes' in-stock bottles, then the type's typical value: a plain bourbon line reads 40%, not 45%, with one bottle of each. A plain line is taken to mean a plain bottle; picking the bottle when logging gives the exact figure.
- **Picker order.** A type line lists the type's own bottles first, then each subtype's bottles under its own heading ("Bonded Bourbon").
- **Same type, both ways.** A subtype bottle's Same type lists the parent's bottles, and a parent-type bottle's lists the subtypes' bottles; the Type column shows which is which.

## Unlinked lines

Decided 2026-11-06. About a fifth of the measured lines in `knowledge` had no link, so logging silently skipped them. Linking fixes the recipe, not just one log, so it writes to the recipe straight away.

- **What counts.** Measured lines (an mL, cL, or oz amount) without a link, plus unmeasured lines whose wording matches an existing ingredient note's name or alias, as described under [reviewing unmeasured lines](#kitchen-staples). Marked garnishes are hidden by default and can be included with **Show garnishes**; unmatched unmeasured lines stay out. A link to a missing note is offered for relinking in logging.
- **The written link.** The amount, any echoed volume ("/ 45 ml."), and the list marker stay as written; the wording is replaced by a path link: `1½ oz [[Cocktails/Types/Gin|gin]]`. Each line is checked against what was reviewed before writing, and a recipe that changed is left alone and reported.
- **Link text.** Decided 2026-11-07. Every link step shows the line as it will read and lets you choose the link's text: **Cabinet name** (`cc-name`, offered even when only its case differs), the text already there (the recipe's wording, a selection, or a link's current text), or your own. Linking someone else's text starts from that text, so changing it is a deliberate choice you see first; **Insert ingredient link** with nothing selected uses the cabinet name. There is no setting: whether a recipe's wording carries nuance is decided line by line. Saving recipe wordings for later recognition (a `cc-written-as` property, or offering aliases) was considered and left for import, where repeated wordings arrive in bulk; aliases stay an ordinary Obsidian feature, which suggestions and pickers match. Superseded by [the link text design](link-text.md) (agreed 2026-11-22; slice 1, the setting and linking new wording, built 2026-11-23): a setting decides when the cabinet name is used without asking, new wording links only the name it contains, and adopting the cabinet name is one step.
- **Logging.** **Link…** on an unlinked measured line or a broken link in Not subtracted, then the link text. After linking, the logging review reloads; choices on other lines carry over while their text is unchanged. Unmeasured lines remain unsubtracted even after bulk linking.
- **Review unlinked ingredients.** A command, not a Base: Bases can't read a note's body lines. Since 2026-11-22 it opens a pane in the right sidebar rather than a modal, so each recipe's name opens it in the main area beside the review (a new tab with Ctrl or Cmd). Since 2026-11-24 it opens as a main-area tab instead, with recipes opening in a split beside it ([upkeep views](#upkeep-views)). It reads the recipes when opened and on its refresh button, not on every change, so choices in progress survive editing a recipe; linking still checks each line against what was read. Since 2026-11-24, reading again (refresh, or switching **Show garnishes**) redraws only the list, and keeps each choice whose wording still covers the same lines; a choice whose lines changed is dropped, since its ticks point at lines by position. Changed 2026-11-25: it also reads again half a second after a cabinet note changes, and after a link refused a recipe as changed. Linking a recipe makes the recipe sync add to `cc-ingredients` about two seconds later, moving every line below it, so a wording linked next in the same recipe was refused on each try until refresh. A read that only moved line numbers takes the new numbers without redrawing, so choices in progress survive; choices are compared by recipe and line text, not line number. Only a read where lines themselves changed redraws the list. Lines are grouped by wording, compared without case or accents, with the groups used by the most recipes first. One choice links a whole group, with each recipe ticked so a different meaning can be left out. Each ticked line is shown as it will read; **As written** keeps each recipe's own spelling, and other text applies to every ticked line. Changed 2026-11-24: each card shows its first three lines before anything is chosen (**Show all** for the rest), since the lines are what tell you what a wording means; choosing a note lists every line with its checkbox, so nothing is linked unseen. The chosen note stays highlighted where it was picked, in the Link to row, and picking another switches to it. Below it, a bar pinned to the bottom of the window while the card is on screen holds everything **Link** will do: "Link 26 lines to Pineapple Juice (type)", **Link shows** as **As written**, the note's name, or **Your own…** (starting on what the Link text setting chose), **Remember**, **Cancel**, and **Link**. A **Change** link above the lines, tried first the same day, could end up far from the button, so a link could be written without seeing what it would show. Suggestions match names and aliases only, as in recipe review.
- **How suggestions rank.** Changed 2026-11-25, from running the suggester over the 336 unlinked wordings in `knowledge`. Names, filenames, and aliases are compared as sets of words, so order doesn't matter (`Tequila (Blanco)` → Blanco Tequila, `aged agricole rhum` → Aged Rhum Agricole), accents, case, and minor words (of, de, and, the) are ignored, and single letters and bare numbers (`Q`, the 2 and 1 of `(2:1)`) never match on their own. A bare parenthetical is part of the ingredient (`Rum (Rhum Agricole)`); a parenthetical or comma text starting "preferably", "such as", "pref.", "ideally", or "like" is a preferred brand; text after a comma or in parentheses starting with to, for, optional, see, or, if, as, about, or plus is a serving note and ignored (`Soda water, to top`). Order: the wording exactly; a note naming the ingredient and its preferred brand together (`gin, preferably Plymouth` → Plymouth Gin); a bottle the line names in full (`rum, preferably Smith and Cross`); a note naming the ingredient exactly; a bottle a hint names part of (`Appleton Signature`); then notes sharing the most words with the ingredient, the broader first on a tie. "or" and "/" still mean alternatives with no suggestion, but only in the ingredient's own words, so "and" in a brand doesn't block it. A category is suggested only by its own name or alias: one shared word put Syrup or Juice ahead of Lime Juice and offered Syrup for every flavored syrup, which a new note fits better. In `knowledge`, measured wordings with no suggestion went from 44 to 53 (only categories lost) and with a category first from 25 to 0.
- **Editing a recipe.** **Insert ingredient link** (in recipes, since 2026-11-24) inserts a path link with the cabinet name, or links the selection. **Link this ingredient line** links an unlinked Ingredients line's wording; **Edit this ingredient link**, with the cursor in a link, changes only that link, since lines often name a type and a preferred bottle. Each is offered only where it applies. The ingredient-note picker lists suggestions, then new notes named from the wording, then every ingredient note. Both write through the editor, so undo works, and do nothing if the text changed while choosing.
- **No "keep as text".** Built 2026-11-06 and removed 2026-11-07: a settings list of wordings the review left out. Nothing needed it: water and similar can be tracked by availability, and a line left as text could never show a recipe as unmakeable once availability queries exist. Every measured line should link to an ingredient note.

## Upkeep views

Decided 2026-11-24, from the question of whether **Tidy this recipe** should reach across recipes, which raised the same question for **Review unlinked ingredients**, **Review missing ABV values**, and **What can I make?**. Main-area tabs and Page Preview built 2026-11-24.

- **Choosing a surface.** One decision about one note is a modal: it's focused and works on mobile, but blocks the note behind it. A list worked through while editing notes, or a report, is a view. Anything answerable from frontmatter is a Base view. A sidebar view suits panels relevant on every note (Outline, Backlinks); in a vault used for more than cocktails, a cabinet pane left in the sidebar stays there for every note, and the user has to notice and close it.
- **Main-area tabs.** **Review unlinked ingredients** and **What can I make?** open as main-area tabs rather than in the right sidebar. A recipe clicked in either opens in a split beside the view, reused for later clicks, so the side-by-side reason for the sidebar is kept; Ctrl or Cmd still opens a new tab. Closing the tab is the familiar way to put it away, and on mobile a tab is a page rather than a drawer. Users can still drag the leaf anywhere; dragged into a sidebar, its links open in the main area as any link would. A view already open, such as one left in the sidebar by an earlier version, is reused where it is. Built 2026-11-24 in `src/ui/view-leaves.ts`; closing the split and clicking again makes a new one.
- **Page Preview.** Recipe and note links in both views fire Obsidian's `hover-link` event and register a hover source, so Cmd or Ctrl hover previews them as in a note. Built 2026-11-24 too: they act like a note's links otherwise. Middle click opens a new tab, and right-click (long press on mobile) shows Open in new tab and Open to the right (not on a phone, where the views use tabs), then what Obsidian and plugins add through the `file-menu` event with source `link-context-menu`, including Open in new window and the cabinet's own note actions. Long press is the plugin's own (500 ms, cancelled by a 10 px drift), since iOS sends no contextmenu for one; Android's contextmenu is folded in so a press opens one menu, and the release doesn't also open the note. The view links skip the system's link preview and text selection on a long press. Checked on desktop with dispatched mouse and touch events (hold, tap, scroll, hold with contextmenu after or before); a real long press on an iPhone opened the menu, and it looked right (2026-11-24). Not yet tried on an iPad or Android. The `obsidian://` links on the Cocktail Cabinet note get no long-press menu, as Obsidian renders them as external links; there'd be nothing in it.
- **Bases over commands.** Upkeep that frontmatter can express becomes a Base view rather than a command: every command sits in the palette for everyone, and a view costs nothing until opened. Views are discoverable from the Cocktail Cabinet note, which mentions each, and properties shown on the note itself. **Review missing ABV values** was retired this way (built 2026-11-24); see [missing values](alcohol-estimate.md#missing-values).
- **Layout in a tab.** Changed 2026-11-24, after the views moved out of the sidebar and Obsidian 1.15 started drawing each standalone setting as a padded card. Both views share one toolbar: a compact row that stays in view, each control with a small label beside it, so they read as controls for the whole list and are the same size in both. **What can I make?** has Uses, Rating, and Tag there; settings-style rows, tried first the same day, made each filter a tall card (an override had also zeroed the card's padding, pushing the names into its corner). **Review unlinked ingredients** has the wording filter, **Show garnishes**, and refresh; the count and how linking works follow as a muted line. Each wording is a card: the wording and its recipe count, then "Link to" with the suggested notes as buttons naming each note's kind, then "or" **Another note…** and **New note…** (formerly **Select link** and **Create…**). Suggestions used to sit under the card, so it was unclear what they belonged to and what they did.
- **What should I buy?** Built 2026-11-24: the **To buy** tab became its own command and tab. It answers a shopping question, not where you'd look when asking what to make, and without it **What can I make?** loses a row of buttons acting as tabs. Both share one base view for reading availability and opening links.
- **No combined pane.** One upkeep pane with sections for unlinked lines, tidying, and missing ABVs was considered, to limit how much the cabinet adds. With tidying staying per recipe and missing ABVs moving to Bases, only the unlinked review is left as a list to work through, and **What can I make?** is a different job (planning a drink).
- **Tidying stays per recipe.** No review across recipes for now, as [agreed for link text](link-text.md#decisions): forms, pasted and page recipes, and `create-recipe` already convert as they read, so new mess is unlikely, and there isn't yet evidence that recipes drift untidy. Revisit if untidy recipes keep turning up, or if changing a note's `cc-name` by hand leaves recipes' link text stale, which nothing catches; renames through Obsidian are followed since 2026-11-24.
- **Mobile.** A view's flow of list, then note, then back is accepted on phones; checked in an emulation pass rather than designed separately. Built 2026-11-24, from that pass: on a phone a note opens in a tab rather than a split, reused the same way, since two columns don't fit; tablets keep the split. Obsidian's mobile emulation runs at tablet width, so the phone case is checked on a phone.

## Classification principles

Agreed on 2026-11-03 while building the [knowledge adoption mapping](knowledge-adoption-mapping.md), which applies them.

- A type exists so its bottles can be swapped; a narrower type needs several real near-substitutes.
- Products without near-substitutes go in their family's catch-all type, as amari do in Amaro. Bottles always have a type.
- Never create a type only one product could belong to; recipes link that bottle directly, with an unowned bottle note if needed. A kind of product with one owned bottle is still a valid type.
- Don't create a type only to give an everyday ingredient a parent; it's a [kitchen staple](#kitchen-staples).
- Families are navigation: choose a reasonable home and merge families whose boundary would be arbitrary.
- Classify by recipe role, not production detail.
- Catch-all names must not read as "any": Specialty Bitters, Flavored Rum. Mark them as [catch-all types](#catch-all-types).
- Migration keeps a recipe link's existing meaning unless its wording says something more specific.
- Directional substitutions are not modeled as types; the logging picker's "Other bottle…" covers them until a substitution feature exists.

## Open decisions

- The classification rules within the category, family, and type levels.
- How cabinet folders, note identification, property names, and links prevent conflicts with unrelated vault content. Longer names such as Cocktail ingredient family and folder scoping are possibilities, not selected solutions.
- Which ingredient types and classifications ship in the starting cabinet.
- How homemade preparations, purchased ingredients, and fresh ingredient sources relate to ingredient types and stock.
- Where optional preparation instructions live and whether any separate preparation records are needed.
- How fresh, bottled, and homemade sources are represented and stocked without unnecessary duplicate ingredient types.
- How to initialize the catalog without implying that the user owns its ingredients.
- How to reuse an existing collection and handle later catalog additions without overwriting personal changes.

## Storage considerations

Folder scoping can limit which notes the plugin handles, but it does not isolate Obsidian property types: a property's assigned type applies to that name throughout the vault. This makes stored property names a separate decision from folder layout and short labels in the plugin UI. See [Obsidian's property documentation](https://obsidian.md/help/properties).

Obsidian links can include folder paths to identify a note when names overlap; choosing how the plugin generates links is still open. See [Obsidian's internal link documentation](https://obsidian.md/help/links).

## First implementation

These are concrete implementation choices for trying the first cabinet flow, rather than a commitment to a final released schema: The [resource schemas](note-properties.md) document the implemented fields, logging, and the shopping list.

- A chosen cabinet root (default `Cocktails`) contains Categories, Families, Types, Bottles, Ingredients, and Recipes folders, plus a Views folder containing six `.base` files and a Cocktail Cabinet note. Notes require both the root scope and an explicit `cc-kind` marker to participate.
- Stored fields use the `cc-` prefix, short for Cocktail Cabinet; plugin UI uses short labels. The prefix namespaces properties without suggesting that each resource is a cocktail recipe. Cabinet property panels use a wider label column, capped at 45% of the available width, to accommodate longer property names without changing other notes' property panels. Wiki links include their vault-relative path and proper name as display text. Browsing uses the core Bases plugin and requires Obsidian 1.9.10 or later; no Dataview dependency is introduced. Each Base filters by cabinet root, Markdown extension, and resource kind, independently of catalog membership or optional parent links. Table columns use the currently implemented properties with friendly labels, and show a note link alongside the proper name. The Cocktail Cabinet note links to all six Bases in context, introducing the collection before types, families, and categories. It avoids embedded tables and schema-specific advice so the page stays useful as properties evolve. **Open cabinet** opens that note rather than a custom browser modal. Family and category creation are available as commands.
- `cc-name` stores the proper name, also shown in the page heading. New note filenames are derived from the proper name by rule, never by per-note exceptions: Latin diacritics fold into plain characters and ligatures are transliterated (ø → oe, so Last Wørd is `Last Woerd.md`); `#2` becomes `No 2` (Tuxedo #2 → `Tuxedo No 2.md`); and a trailing initialism loses its periods (Maison Rouge Cognac V.S. → `Maison Rouge Cognac VS.md`). Proper names may contain `#` and periods. Names such as Cachaça, Añejo Tequila, and Crème de Menthe retain the existing plain filenames and catalog IDs. Names that differ from their filename also become Obsidian aliases, and plugin pickers include the proper name, filename when it differs, and aliases. Older notes without the name property fall back to their filename.
- Family notes link to a category through `cc-category`; type notes link to a family through `cc-family`. Both are optional single links (changed from lists on 2026-11-04, matching `cc-type` and the principle that families are navigation with one home). Links outside the supported adjacent levels are ignored by the hierarchy reader.
- The bottle form links each bottle to at most one ingredient type through a scalar `cc-type` link and records bottle volume and fractional ABV. It defaults to volume tracking with open mL and unopened count, and also offers manual status tracking. Only active stock fields are written. Open stock defaults to the full bottle volume until the user changes or clears the amount; later bottle-volume edits preserve the entered percent or mL. Blank measured amounts remain unknown; a blank unopened-bottle count means zero. Open mL must not exceed known full bottle volume.
- The other-stock form links sources through `cc-provides`, with `cc-form` independent of its selected stock mode. Status tracking is the default; volume tracking stores remaining mL. Fresh fruit and bottled juice can supply the same ingredient type. Both stock forms support optional last purchase price and an independent shopping flag; ingredient types also have a shopping flag. Preparation batches and measured yields remain outside the current scope.
- Ingredient types have no built-in Brix field or default Base column. Default sugar syrups state a sugar-to-water ratio by weight; nominal concentration details remain in their descriptions rather than structured properties. Ratio filenames use “1 to 1” and “2 to 1” for cross-platform validity.
- Recipes preserve `rating`, `source`, a resolved local `created` date, and the existing Ingredients, Method, Description, and Tasting Notes sections. Creation accepts plain text copied from a recipe and opens an editable ingredient review, with manual entry also available. **Convert note to recipe** reviews the active Obsidian page directly, retaining its properties, rating, and creation date. On save, pages outside the cabinet move into Recipes with their original filename; pages already inside the cabinet retain their path. The destination is shown before saving, and conflicting filenames or source edits prevent overwriting. Name and source use full-width fields. References can target every hierarchy level, a bottle, or other stock; plain-text ingredients remain possible and are explicitly labeled. Link suggestions use note names, filenames, and aliases and require acceptance, retaining source wording as link display text. The creation menu offers every ingredient resource kind; new ingredient notes are saved independently of the recipe. Amounts remain source text, with a conservative interpretation of single mL/cL/US fl oz volumes. Ambiguous measurements and ingredient alternatives need decisions during future consumption workflows; recipe creation does not deduct stock. Plain text and Markdown parsing are local and do not fetch web pages. Familiar ingredient amounts and following method paragraphs are recognized without headings; uncertain content remains in Description for review. See [recipe properties](note-properties.md#cocktail-recipe) for parser boundaries and preservation behavior.
- Setup is create-only for notes and preflights conflicts. Existing `.base` files at the expected view paths are replaced with the current version. Conflicting folders, files that block folders, and paths differing only by case stop setup. `cc-catalog-id` recognizes starter notes across renames within the root, preserving their content. IDs use a slash between the level and identity, such as `family/Aquavit`, to avoid Obsidian treating a colon as a URL scheme. Starter IDs use the current catalog name, such as `family/Apple Brandy Family`. Reruns fill missing pages without updating existing catalog descriptions or deleting retired entries. This is not an automatic migration flow.
- The catalog is an authored first draft for review, especially its rum and liqueur distinctions. It supplies definitions and named bottle references with unknown availability, without asserting owned stock. A new cabinet also gets the worked example described under [homemade stock](#homemade-stock). During initial development, update catalog IDs to match revised starter names and adjust the dev vault directly; do not retain obsolete IDs or add compatibility mappings for earlier development versions.
