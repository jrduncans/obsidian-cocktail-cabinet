# Resource schemas

Schemas for Cocktail Cabinet resources. The `cc-` prefix means Cocktail Cabinet; it namespaces properties without implying that every resource is a cocktail recipe. Obsidian's standard `aliases` property and the existing recipe properties `created`, `source`, and `rating` keep their unprefixed names.

Creation forms implement per-record volume or status tracking, mL remaining, last purchase price, and shopping-list flags. Consumption is available through **Log this cocktail**; flagged resources appear in the **Shopping list** note. The plugin validates creation inputs and selected stock during logging, not every manually edited property; existing notes are preserved rather than automatically migrated.

## Reading the schemas

Each resource below lists its own frontmatter properties with a **Type**, a boolean **Required** flag, and a description of its use.

- `Required: true` means the property is required by the resource schema. `false` means omission is supported. For stock resources, the selected mode is required for stock behavior; general resource browsing only checks the root scope and kind marker. Creation forms can require additional input, and generated notes can include optional properties; those rules are described explicitly.
- `string` is YAML text. `number` is a YAML number. `integer` is a whole number. `date` is a local calendar date stored as `YYYY-MM-DD`.
- `T[]` is a list of values of type `T`. `link<Resource>` is a quoted wiki-link string pointing to a cabinet resource of that type. For example: `"[[Cocktails/Families/Rum|Rum]]"`. Hierarchy parents (`cc-type`, `cc-family`, `cc-category`) are single link strings: each note has one home. Only `cc-provides` is a list, because one piece of other stock can provide several types (limes provide lime juice and lime peel).
- `null` is an explicit unknown value, distinct from zero, except for stock amounts: a missing, null, or blank `cc-open-ml`, `cc-unopened`, or `cc-remaining-ml` means zero (decided 2026-11-06). Bottle size and price stay unknown when blank. Optional properties may be absent; a type containing `null` additionally permits an explicit null value.
- `unknown` identifies a field whose value type has not yet been defined. It is not a claim that a value has been validated.

Ordinary resources must be Markdown files inside the selected cabinet root, which defaults to `Cocktails`. The plugin uses `cc-kind` to recognize each resource; subfolders organize new files but do not determine their type. Relationship targets must resolve to recognized resources of the expected kind inside the cabinet. Invalid or unresolved relationships are ignored. Bottles may have one ingredient-type link or none; lists in `cc-type` are ignored. Other relationships support empty lists and multiple links.

Creation forms validate their inputs. The plugin does not currently validate every property of manually edited resources. Setup preserves existing resources rather than synchronizing their content with the starter catalog.

## Ingredient category

A broad classification of ingredient families, such as Spirit or Juice. New notes are placed in `<root>/Categories/`.

| Property        | Type         | Required | Description and use                                                                                                                                                                                                              |
| --------------- | ------------ | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cc-kind`       | `"category"` | `true`   | Identifies an ingredient category for browsing, classification, and related-recipe discovery.                                                                                                                                    |
| `cc-name`       | `string`     | `false`  | Proper display name used in plugin lists, pickers, detail titles, and new link display text. Generated from the required Name input. Falls back to the filename without its extension if absent or unusable.                     |
| `aliases`       | `string[]`   | `false`  | Alternate names for Obsidian links and plugin picker search. Creation adds the proper name when it differs from the plain Latin filename.                                                                                        |
| `cc-catalog-id` | `string`     | `false`  | Starter identity, such as `category/Spirit`. Needed on starter resources for setup to preserve identity across file renames and use the current path for new links. Omitted on user-created resources. Duplicate IDs stop setup. |

Categories have no broader classification property. Their description lives in the note body and is not interpreted by the plugin.

## Ingredient family

An optional grouping of ingredient types, such as Rum or Bitters. A family may belong to categories or stand alone. New notes are placed in `<root>/Families/`.

| Property        | Type                        | Required | Description and use                                                                                                                                            |
| --------------- | --------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cc-kind`       | `"family"`                  | `true`   | Identifies an ingredient family for browsing and related-recipe discovery.                                                                                     |
| `cc-name`       | `string`                    | `false`  | Proper display name for plugin UI and new links. Generated from the required Name input; falls back to the filename if absent or unusable.                     |
| `aliases`       | `string[]`                  | `false`  | Alternate names included in picker search and available to Obsidian links.                                                                                     |
| `cc-catalog-id` | `string`                    | `false`  | Starter identity, such as `family/Aquavit`. Setup uses it to recognize renamed starter resources and reject duplicates. User-created families do not need one. |
| `cc-category`   | `link<Ingredient category>` | `false`  | The family's category. Read for linked-resource browsing and related-recipe traversal. No category is inferred from the family name.                           |

The description lives in the body. Missing categories do not make a family incomplete or invalid.

Descriptions, optional concentration details, and Preparation instructions live in the body. They are not parsed as frontmatter properties or preparation batches. Brix is not a built-in property or default Base column. Earlier notes may retain `cc-brix` as a custom property; the plugin does not remove it. Existing Bases are preserved too, so remove their Brix column manually if desired.

## Bottle

A named bottle, together with its recorded stock. One note tracks the open amount and any unopened bottles of the same size and strength. New notes are placed in `<root>/Bottles/`. The creation form writes the selected stock mode and its applicable fields.

| Property                 | Type                    | Required | Description and use                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------ | ----------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cc-kind`                | `"bottle"`              | `true`   | Identifies a bottle for cabinet browsing and recipe ingredient selection.                                                                                                                                                                                                                                                                                                                                                                                            |
| `cc-name`                | `string`                | `false`  | Proper display name for plugin UI and new links. Generated from the required Name input; falls back to the filename if absent or unusable.                                                                                                                                                                                                                                                                                                                           |
| `aliases`                | `string[]`              | `false`  | Alternate names included in picker search and available to Obsidian links.                                                                                                                                                                                                                                                                                                                                                                                           |
| `cc-type`                | `link<Ingredient type>` | `false`  | The bottle's single recipe-facing ingredient type, used for linked-resource browsing and related-recipe discovery. Omitted when unclassified. Bottles sharing this type can appear as same-type alternatives; sharing a family alone is insufficient. Lists are ignored rather than selecting or combining types.                                                                                                                                                    |
| `cc-stock-tracking`      | `StockTracking`         | `true`   | Selects `volume` or `status` for this bottle record. This choice determines the applicable stock fields below. The creation default is `volume`, saved explicitly rather than inferred from a missing property.                                                                                                                                                                                                                                                      |
| `cc-volume-ml`           | `number \| null`        | `false`  | Full volume of one bottle in milliliters, greater than zero when known, such as `750`. A missing or null value is unknown. Used for bottle rollover during logging; remains useful descriptive metadata in status mode.                                                                                                                                                                                                                                              |
| `cc-abv`                 | `number \| null`        | `false`  | Alcohol strength as a fraction from 0 to 1. The existing form accepts 0–100 percent, so `40` stores `0.4`; blank stores `null`. Stock tracking changes do not change the representation of ABV.                                                                                                                                                                                                                                                                      |
| `cc-open-ml`             | `number \| null`        | `false`  | **Volume mode only.** Nonnegative mL remaining in the open bottle, excluding unopened bottles. Must not exceed the known full bottle volume. Missing, null, or blank means no open stock, the same as zero; a blank value is read as 0 but not rewritten. The form defaults to 100% full once bottle volume is entered, supports percent-full estimates or direct mL, and displays the converted quantity. Clearing the amount saves 0. Logging deducts mL directly. |
| `cc-unopened`            | `integer \| null`       | `false`  | **Volume mode only.** Nonnegative count of unopened bottles. Missing, null, or blank means zero. Creation saves zero when the input is empty. Logging uses this count and full bottle volume when another bottle must be opened; it preserves an existing blank if the count does not change.                                                                                                                                                                        |
| `cc-availability`        | `Availability`          | `false`  | **Status mode only.** Manual `Unknown`, `Have`, `Low`, or `Out`; missing means `Unknown`. Creation writes the chosen status explicitly. Pours do not automatically decrement or change this status.                                                                                                                                                                                                                                                                  |
| `cc-last-purchase-price` | `number \| null`        | `false`  | Nonnegative numeric amount last paid for one bottle, with zero valid and missing or null meaning unknown. Purchasing metadata, independent of stock mode. No price history, currency conversion, or cost calculations are defined.                                                                                                                                                                                                                                   |
| `cc-shopping-list`       | `boolean`               | `false`  | Explicitly marks this bottle for purchase when `true`. Missing means `false`. Independent of current stock level and of any flag on its ingredient type; listed in the shopping list's Bottles section.                                                                                                                                                                                                                                                              |
| `cc-last-used`           | `date \| null`          | `false`  | Date (`YYYY-MM-DD`) this was last used in a logged cocktail: selected for a line, or the one source a line clearly uses without subtracting (status-tracked, or no mL amount, such as dashes). Written by **Log this cocktail**, never moved backward; Edit stock doesn't set it. Missing means not used since tracking began. Orders Restock's Running low and Out, most recently used first.                                                                       |
| `cc-last-purchased`      | `date \| null`          | `false`  | Date (`YYYY-MM-DD`) this was last recorded as bought, by **Record purchases** or **Bought more**; never moved backward. Only the last purchase is kept, with `cc-last-purchase-price`.                                                                                                                                                                                                                                                                               |

Earlier development notes that store `cc-family` or `cc-category` as a list need the same conversion to one quoted link string; a list is ignored, leaving the note without a parent.

Earlier development notes using `cc-types` need manual conversion: select one ingredient type, store its quoted wiki link as the scalar `cc-type`, and remove `cc-types`. The reader does not fall back to the old property or choose between multiple types. Update preserved bottle Bases to use `note.cc-type` in their property configuration and column order; setup does not overwrite them.

Starter bottle references, such as Angostura Bitters classified as Aromatic Bitters, use status tracking with Unknown availability. Their existence does not establish ownership; quantities, bottle size, strength, and purchase intent are not inferred. Recipes can link to the same bottle note before and after the user records stock.

Only the selected mode's stock fields apply: volume mode has open mL and unopened count; status mode has qualitative availability. Full bottle volume, ABV, price, and the shopping flag remain independent metadata in either mode. The description lives in the body.

When all quantities are known, total volume is `open mL + unopened count × bottle volume mL`; it is derived rather than stored separately. Blank amounts count as zero. Opening an unopened bottle requires a known bottle volume and a positive unopened count. The model records one open-bottle amount rather than several separately measured open bottles.

`StockForm` is one of `Fresh ingredient`, `Prepared juice`, `Bottled juice`, `Homemade syrup`, `Purchased syrup`, `Kitchen staple`, or `Other`. The source description lives in the body. Measured juice yields, individual preparation batches, and multiple container sizes are not defined by this schema.

## Stock tracking rules

`StockTracking` is the enum `volume` or `status`. `Availability` is the enum `Unknown`, `Have`, `Low`, or `Out`. The tracking mode is selected independently on each bottle or other-stock record. It does not belong on categories, families, or ingredient types: those describe recipe-facing ingredients, not owned quantities.

| Mode     | Authoritative stock                                                                              | Consumption and availability behavior                                                                                                                                                                                                  |
| -------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `volume` | For bottles: `cc-open-ml`, `cc-unopened`, and bottle volume. For other stock: `cc-remaining-ml`. | Deduct measured pours in mL. Blank amounts are zero. Compare the quantity with a recipe's requirements when assessing whether it is sufficient, and report a shortfall rather than inventing stock.                                    |
| `status` | `cc-availability`: `Unknown`, `Have`, `Low`, or `Out`.                                           | Preserve the user's status during drink logging. `Have` and `Low` can indicate qualitative availability, but do not prove enough for a given number of servings. `Out` means unavailable and `Unknown` makes no claim of availability. |

The mode is the sole authority for stock: inactive-mode fields must not be written by creation or a mode change, and must not influence future stock calculations if manually left behind. Changing modes must be an explicit user action that initializes the new mode; it must not infer a numerical amount from `Have`, or silently choose a qualitative status from the previous volume. A missing mode is incomplete stock configuration, not an invitation to guess from the resource kind. General note browsing may still recognize the resource through `cc-kind`.

Volume is stored as mL remaining. The mL used is an input to a consumption operation, not a cumulative stock field. Estimated starting quantities are allowed. The bottle creation form starts in percent-full entry and defaults to 100% when a valid bottle volume is entered. It also accepts mL directly and shows the resulting mL. A positive percentage requires a known full bottle volume; zero percent means zero mL even without it. Changing bottle volume preserves any explicitly entered percent or mL, including blank and zero; the untouched full-bottle default follows volume changes. Switching input units converts the current amount when possible and reports missing volume or invalid input without discarding the entry. Percentages are not persisted. The creation form resets measured amounts to unknown and the unopened-bottle count to zero when switching modes. Existing notes are edited with **Edit stock**, which initializes a new mode explicitly and removes the old mode's stock fields; hand edits through Obsidian properties or Bases must do the same. A record may explicitly have unknown quantities.

Status tracking has no automatic Low threshold or depletion. Fresh fruit in status mode does not acquire an inferred juice yield. Replenishing an existing source updates its current stock; this schema does not require a batch record for each syrup preparation.

## Upgrading early stock notes

Setup preserves existing notes and views. It does not convert the initial fraction schema automatically. Before recording more stock in an early cabinet:

1. For each old bottle, set `cc-stock-tracking` to `volume`. Convert a known `cc-open-fraction` using `cc-open-ml = cc-open-fraction × cc-volume-ml` (for example, `0.5 × 750 = 375`). Keep `cc-unopened`, full bottle volume, and ABV unchanged. Remove `cc-open-fraction` after conversion.
2. A missing, null, or zero fraction means none open (`cc-open-ml: 0`). If the fraction is positive but full volume is unknown, find the full volume or enter a current mL estimate before replacing that quantity; do not invent a volume. Review invalid fractions or amounts exceeding full volume instead of converting them blindly.
3. For each old other-stock source using qualitative availability, set `cc-stock-tracking` to `status` and retain its status; missing availability means Unknown. Do not infer mL from Have or Low.
4. In existing Bases, replace the fraction column with `cc-open-ml` and add tracking mode, remaining mL, status, and purchasing columns as needed. Existing home notes are user-owned: remove obsolete stock-unit advice and link to the resource views. Rerunning setup only adds missing files.

Prices and shopping flags are optional; omitted prices stay unknown and omitted flags mean false.

## Purchasing and the shopping list

Types, bottles, and other-stock sources share `cc-shopping-list: boolean`, optional with an effective default of `false`. It records purchase intent, independently of tracking mode and stock state. Empty stock does not automatically set it, and positive stock does not automatically clear it.

The **Shopping list** note (`<root>/Shopping list.md`, embedding `Views/Shopping list.base`) includes recognized cabinet resources of kind `type`, `bottle`, or `ingredient` whose `cc-shopping-list` is exactly `true`. A type-level entry means a generic need, such as Lime Juice; a bottle-level entry names the particular bottle; an other-stock entry names that source. Flags do not propagate between linked resources. If both a type and its bottle are explicitly flagged, both entries remain visible rather than one being silently hidden or merged. A source counts as in stock when volume-tracked with a positive open, unopened, or remaining amount, or status-tracked as Have or Low; Unknown and Out are not in stock.

`cc-last-purchase-price` belongs to actual bottle or other-stock records. Ingredient types remain classifications and generic shopping needs rather than holders of a particular purchase's price. Prices are plain numeric amounts in the user's consistent currency convention, without currency symbols, inferred currency, or automatic conversion. Missing prices remain unknown, and shopping entries do not require a price. Mixed-currency accounting, purchase history, pack pricing, and automatic clearing of shopping flags on purchase are outside this schema change.

For example, these are two representations of the same source with different bookkeeping preferences:

```yaml
cc-kind: ingredient
cc-name: Homemade simple syrup
cc-provides:
    - '[[Cocktails/Types/Simple Syrup (2 to 1)|Simple Syrup (2:1)]]'
cc-form: Homemade syrup
cc-stock-tracking: volume
cc-remaining-ml: 500
cc-shopping-list: false
```

```yaml
cc-kind: ingredient
cc-name: Homemade simple syrup
cc-provides:
    - '[[Cocktails/Types/Simple Syrup (2 to 1)|Simple Syrup (2:1)]]'
cc-form: Homemade syrup
cc-stock-tracking: status
cc-availability: Have
cc-shopping-list: false
```

Recipe requirements are Markdown body content rather than frontmatter properties:

| Body section  | Type            | Required | Description and use                                                                                                                                                                                                          |
| ------------- | --------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ingredients   | `Markdown list` | `false`  | Creation requires at least one ingredient and writes the entered amount plus a link or plain text. Logging reads its lines. Its links are copied into `cc-ingredients`, which the Recipes sections in ingredient notes read. |
| Method        | `Markdown`      | `false`  | Preparation steps; written by the recipe form and not interpreted.                                                                                                                                                           |
| Description   | `Markdown`      | `false`  | Recipe description; written by the form and not interpreted.                                                                                                                                                                 |
| Tasting Notes | `Markdown`      | `false`  | Older personal notes. Not a form field: text a source or existing note has is kept as written, and new recipes get no heading. Impressions belong in the daily note, beside the drink's “Made …” line.                       |

Linked requirements can reference an ingredient category, family, type, specific bottle, or other-stock source. A source's `cc-provides` links participate in related-recipe traversal. The form offers suggestions by name, filename, and alias, without automatically linking ingredients or inferring style defaults, substitutions, or inventory bottle choices. Accepted links retain the ingredient's entered wording as display text. Existing Markdown wiki links are preserved unless explicitly replaced or unlinked. Plain-text ingredients remain valid but cannot be resolved through the classification graph.

Recipe review accepts copied plain text, bullet lists, or structured Markdown. Familiar leading amounts identify ingredients without headings; a following paragraph beginning with a preparation verb is treated as Method. Parenthetical brands participate in link suggestions without changing source text. Structured pages can use a title and ingredient list, with Method/Directions/Instructions, Description/Notes, and Tasting Notes sections. For copied-text creation, frontmatter name/source and numeric rating are read; other properties are placed in Description for review. Creation uses a new local date. **Enhance as cocktail recipe** instead keeps all existing frontmatter values, including nested properties, aliases, rating, and creation date, while updating the name, source, and recipe kind. YAML may be reformatted. Notes outside the cabinet move to `<root>/Recipes/<existing filename>` through Obsidian’s file manager; notes inside the cabinet keep their path. The review shows the destination. Saving checks the source has not changed and refuses conflicting filenames. A failed move restores the original content only if no concurrent edit would be overwritten. Unknown sections and indented ingredient continuations are retained in Description with a warning, and the original text is available during review. Missing recipe details remain blank.

Amounts remain text in the ingredient list, with no duplicate structured quantity property. The form recognizes single positive volumes in mL, cL, and US fluid ounces (`29.5735295625 mL` per ounce), including decimal and mixed or Unicode fractions, to show an interpretation. Explicit non-volume equivalents such as `1 barspoon (1/8 oz)` use the stated volume; a bare barspoon or teaspoon counts as one US teaspoon (4.92892159375 mL) and a tablespoon as three; no volume is assumed for a bare dash. Parenthetical volume equivalents such as `2 oz (60 ml)` use the stated mL rather than converting the ounces, in either order. Both quantities must be precise and positive. Ranges, qualified amounts, and volume pairs without a single explicit mL amount remain uninterpreted. Recipe creation does not perform inventory arithmetic or choose an alternative. **Log this cocktail** treats each linked ingredient line as one pour, selects one bottle or measured source, and deducts the reviewed volume. Related-recipe discovery does not rewrite requirements or consider recorded stock quantities and availability.

## Cabinet home

The cabinet landing note, written at exactly `<root>/Cocktail Cabinet.md`. Setup detection requires both this path and the kind marker. It is not included in ingredient, stock, or recipe browsing.

| Property            | Type        | Required | Description and use                                                                                                                                                   |
| ------------------- | ----------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cc-kind`           | `"cabinet"` | `true`   | Identifies the home note when the plugin checks whether the selected cabinet is set up.                                                                               |
| `cc-name`           | `string`    | `false`  | Written as `Cocktail Cabinet`. No current runtime behavior reads the home note's display name.                                                                        |
| `cc-schema-version` | `integer`   | `false`  | Written as `1`. No runtime reader checks it; it does not select a parser, run migrations, or enable compatibility handling. It has no current behavioral requirement. |

The body starts with command-palette guidance for adding stock and recipes, then introduces bottles, other stock, and recipes before the ingredient reference catalog. It links to all six resource Bases in `<root>/Views/` as it explains the concepts, with types, families, and categories in order. It explains that catalog membership does not imply owned stock, how to edit the tables, where each note lists related recipes, and the note header and More options actions. It contains no embedded tables or stock-unit instructions; the linked views query current notes rather than enumerate the starter catalog. Setup creates the home when missing and preserves it when present; older home notes need their new Base links added manually.

## Resource Bases

Setup creates `Ingredient categories.base`, `Ingredient families.base`, `Ingredient types.base`, `Bottles.base`, `Other stock.base`, and `Recipes.base` in `<root>/Views/`. These files are core Obsidian Bases configuration, with no frontmatter resource marker and no plugin runtime dependency. Each filters Markdown files inside the cabinet root by the corresponding `cc-kind`; parent properties and catalog IDs are not required. The cabinet home is not a seventh resource Base. Setup also creates `Restock.base`, a formula Base with three tables of bottles and other stock: Running low (Low, or the last bottle at or under the **Running low: percent full** setting, default 10%; without a bottle size, and for other stock tracked in mL, at or under **Running low: mL**, default 70), Out (Out, or nothing above 0 open or sealed, blank counting as 0), and Unknown (Unknown or missing availability, or no tracking mode). Running low and Out list the most recently used first (`cc-last-used`), then the never-used by name. Each shows `cc-shopping-list` as an editable checkbox. The settings are written into the `lowShare` and `lowMl` formulas. `Recipes.base` also has **Latest**, sorted by `created` descending, and **Recently made**, sorted by `cc-last-made` descending.

The `.base` files in `<root>/Views/` belong to the plugin. Setup replaces any that differ from the current version, and on startup the plugin rewrites a view when a release or a setting changes it (it records the version it last wrote in its data, so column widths or sorting saved by Obsidian stay until then). **Refresh cabinet views** rewrites every changed or missing view. To keep a changed view, copy it into `<root>/Custom views/`, which setup creates and the plugin never touches.

Each table starts with **Name**: the proper name (`cc-name`, else the file name) as a link, so it opens and previews like a file link; there are no separate file-name and `cc-name` columns. The resource's current creation fields follow. Recipes show Rating (as stars; unrated is empty), Last made, Times made, Created, then Source, last so it scrolls off first on narrow screens. Missing optional values stay empty. Stock views show the selected mode, mL quantities, availability, price, and shopping flags. Ingredient types show their shopping flag too. ABV is labeled as a fraction; open stock is labeled in mL. New notes populate only the selected mode’s stock fields; Bases also display inactive fields if a user manually leaves them behind. Users can edit filters and columns in Obsidian; setup keeps existing `.base` files at these paths, even when their configuration has changed.

## Naming and starter identity

The display name, filename, catalog ID, and page heading have separate roles. Creation writes the name property and heading, generates a plain Latin filename, and supplies proper-name display text for new links. The reader uses a nonblank name suitable for link display; otherwise it falls back to the filename.

There is no ongoing synchronization between these representations. Editing `cc-name` by hand affects subsequent plugin displays and newly generated links; it does not rename the file, rewrite the heading, or update existing links' display text. **Rename cabinet note** keeps them in step; see [renaming](cabinet-design.md#renaming).

`cc-catalog-id` is optional for custom resources but must be retained on starter categories, families, types, and bottle references for setup to preserve their catalog identity across renames. IDs use a slash between the level and identity, such as `family/Aquavit`, to avoid URL-scheme rendering. Catalog identity is independent of the display name and path. Browsing and recipe discovery do not use it.
